polyring

Groth16-in-Groth16 recursion for gnark. Verify a BN254 or BLS12-381 Groth16 proof inside a BN254 Groth16 circuit, and on-chain.

GitHub Readme Getting started The paper
Unaudited research software. v0.1, pre-1.0, no releases yet. Do not use it to secure funds, and read the security policy before reporting anything.

The trade

A Groth16 verifier circuit is dominated by one thing: the pairing check. polyring evaluates the same identity gnark does, but over a polynomial ring instead of over 𝔽p¹², so the prover does far less work. The on-chain verifier pays for it: the ring checks draw three BSB22 commitments instead of one, and the contract has to check each of them.

Outer verifier over a BN254 inner proof, measured on a simulated EVM. Reproduce with go test ./examples/recursion/ -run TestOuterOnChain -v. The constraint counts are exact; the timings are indicative.

When it pays

You prove the outer proof

Fewer constraints is less proving time, less setup time and less money at a service that prices by the constraint.

You verify a BLS signature in-circuit

The same technique applies to signature verification, which is where it comes from.

You work on recursive SNARKs

A reference implementation for BN254 and BLS12-381, with the curve split cleanly from the shared core.

You want a faster PairingCheck

lib/gnarkpairing gives you both circuits from the same verifying key, so you can A/B them in your own project.

Install

go get github.com/mistcash/polyring

go test ./examples/recursion/ -run TestGroth16Verifier -v

How it works

The pairing is evaluated over the polynomial ring 𝔽p[w]/(w¹² − 2ξ₀w⁶ + ξ₀² + 1) — x¹² − 18x⁶ + 82 for BN254, x¹² − 2x⁶ + 2 for BLS12-381 — with deferred product checks, following On Proving Pairings. Only e(A,B) runs the full Miller loop; e(α,β) is folded in as a constant previous value and e(L,γ), e(C,δ) use precomputed lines.
